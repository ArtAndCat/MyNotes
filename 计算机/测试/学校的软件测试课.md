##### 软件开发模型：
###### 5个典型的软件开发模型
软件开发模型的定义：软件开发模型规定了软件开发的步骤   
- 瀑布模型：就是刚刚学的（上面的）  问题定义改计划  （不适合现代软件开发）
    分阶段进行  一步一步的进行  
    缺点：需求会不断变化！因为一步一步进行  需求变化后  代码就是地狱  ......  需求可能有偏差
    用于：需求不会变化 大项目
- 快速原型模型：
    需求分析 -> 构建原型 -> 原型评价 （不符合？回退到“需求分析”（细化需求）-> 确定最终需求 -> 软件开发
    缺点：需求阶段花费时间较多  
- 迭代模型：（增量模型）
    开发功能模块1  然后模块2  
    <  需求分析 -> 软件设计 -> 编码 -> 测试  > \* N  
    缺点：因为前期代码的扩展性  屎山代码
    适合小项目
- 螺旋模型：
    计划 -> 风险分析 -> 开发 -> 用户评估 （反复循环）
    强调风险分析 每一轮都有原型
    缺点：管理复杂 成本高 需要风险分析经验
    用于：大型复杂项目 风险高的系统（航天 军工 金融...）
- ==敏捷开发模型：==（20世纪90年代）
    把项目拆成小份 每次只做一个版本（2-4周）
    每轮都有：计划 -> 设计 -> 编码 -> 测试 -> 交付
    ==强调沟通== 快速响应变化 ==用户全程参与==
    缺点：文档少 后期维护难 依赖团队水平
    用于：需求变化快的互联网项目 创业公司  ==小项目==
    核心：==调动所有人  以用户为核心  合作  沟通==  过程大于一切  简化文档  注重最后结果


软件质量概述   实用性和寿命
概念 p6 中间
软件质量：6个质量点
- 功能性：适合性  准确性  互操作性  依从性  安全性  
- 可靠性：成熟性 容错性 易恢复性
- 易用性：易理解性 易学性 易操作性
- 效率：时间特性 资源特性
- 可维护性：易分析性 易改变性 稳定性 易测试性
- 可移植性：适应性 易安装性 共存性 易替换性

1.2 软件缺陷管理 
软件缺陷产生的原因（deepseek）
- 需求阶段：需求理解错 需求不明确 需求老在变
- 设计阶段：设计有漏洞 逻辑不严谨 架构不合理
- 编码阶段：代码写错 变量用错 边界没考虑
- 测试阶段：测试不充分 用例没覆盖 环境不一样
- 文档阶段：文档写错 文档更新不及时
- 沟通问题：需求没传达到 团队配合不好

缺陷报告核心要素
- ID：每个bug的唯一编号，方便查找和管理
- 标题：简洁明了地概括问题，如“登录页点击登录无响应”
- 严重程度：bug的影响程度（致命/严重/一般/轻微）
- 优先级：修复的紧急程度（高/中/低）
- 测试环境：操作系统、浏览器、设备等信息
- 前置条件：复现bug前需要满足的条件
- 复现步骤：详细描述如何操作才能出现bug
- 实际结果：操作后实际发生的情况
- 预期结果：应该发生的正确结果
- 附件：截图、日志、录屏等辅助信息
- 可重现BUG：能稳定复现的bug，开发才好修
- 简洁：描述要简短清楚，一看就懂怎么操作

软件测试与软件开发的关系

· 相辅相成：开发和测试就像硬币的两面，缺一不可
· 早期介入：测试越早参与，发现问题成本越低
· 质量保障：开发写代码，测试保质量，共同目标是好软件
· 相互促进：测试找bug倒逼开发写更好代码，开发写得好让测试更轻松
· 相爱相杀：测试和开发日常"打架"，但都是为了产品好
· 生命周期：开发在前测试在后，但测试贯穿全程（需求评审就要参与）
· 左右手关系：左手开发右手测试，配合好才能出活

# 第二章  黑盒测试方法   p28

## 2.1 等价类划分

黑盒测试方法，将输入按规则分组，每组选一个代表值测试，减少用例量。

### 2.1.1 等价类划分的基本概念与原则

#### 1. 划分等价类与4个原则

**划分**：

- 有效等价类：合法输入
- 无效等价类：非法输入

**四个原则**（P29）：

1. 完备：所有输入都要归入某个类
2. 无冗余：每个输入只属一个类
3. 代表：每类取一个值代表测试
4. 边界敏感：注意边界值，常结合边界值分析

#### 2. 设计测试用例

**步骤**：

1. 分析输入条件
2. 划分有效/无效等价类
3. 编号
4. 设计用例：
    - 有效类：一个用例可覆盖多个
    - 无效类：每个无效类单独设计用例（防屏蔽）

**例**：输入1~100整数
- 有效：50
- 无效：0, 101, “abc”（各单独用例）
